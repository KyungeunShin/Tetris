# 안전한 리팩터링

이 스킬은 기능과 공개 API를 유지하는 범위에서 코드를 직접 리팩터링한다. PRD.md와 README.md, 변경 대상, 기존 테스트를 확인하고 입력·반환값·export·상태 전이·DOM 연결 등 보존할 계약을 정리한다.

변경 전에 관련 테스트와 프로젝트의 필수 검증을 실행하고 명령·결과를 기록한다. 테스트가 실패하거나 실행할 수 없으면 제품 코드를 변경하지 않고 문제를 보고한다. 필요한 회귀 테스트는 기존 동작을 검증하도록 먼저 추가하고 통과를 확인한다. 작은 변경 단위마다 같은 검증을 실행하며 실패하면 자신의 변경을 수정하거나 되돌린다. 다른 사용자의 변경을 되돌리지 않는다. 마지막으로 변경 전과 동일한 검증 전체가 통과하는지 확인한다.

## 점검 체크리스트

- [ ] 변경 전 기준 상태
  - 통과: 관련 테스트와 필수 검증이 모두 통과하고 실행 근거가 있다. 실패: 기존 실패·미실행·핵심 동작 검증 부재로 기준 상태를 확정할 수 없다.
- [ ] 기능 보존
  - 통과: 이동·회전·하강·고정·점수·종료·재시작의 관찰 가능한 결과가 동일하다. 실패: 규칙·타이밍·사용자 동작이 달라진다.
- [ ] 공개 API 보존
  - 통과: 외부에서 사용하는 이름·인자·반환값·export 및 DOM 연결 계약이 유지된다. 실패: 호출자나 기존 사용법을 바꿔야 한다.
- [ ] 구조 개선의 범위
  - 통과: 책임 분리·중복 제거·이름 개선의 목적이 명확하고 필요한 코드만 변경된다. 실패: 새 기능·규칙 수정·무관한 설정 변경이 섞인다.
- [ ] 테스트 신뢰성
  - 통과: 기존 기대값을 유지하고 실제 동작을 검증하는 테스트가 통과한다. 실패: 실패를 숨기려고 테스트를 삭제·건너뛰거나 기대값을 변경한다.
- [ ] 변경 후 검증
  - 통과: 변경 전과 같은 테스트·필수 검증이 모두 통과하고 관련 UI가 있다면 화면·입력 회귀 확인도 완료한다. 실패: 실패·미검증이 남거나 변경 전후 결과를 제시하지 못한다.

## 보고

변경 파일과 구조 개선 효과, 보존한 계약을 요약한다. 다음 표에 실제 명령, 테스트 수 또는 종료 코드 등의 근거를 기록하며 실행하지 않은 결과를 통과로 쓰지 않는다.

| 검증 명령·시나리오 | 변경 전 결과 | 변경 후 결과 |
| --- | --- | --- |

미해결 문제는 다음 표로 보고한다. 높음은 동작·API 변화나 테스트 실패, 중간은 검증 부족·구조 개선 장애, 낮음은 국소적 가독성 문제다. 기준 검증을 확보하지 못한 경우 리팩터링을 수행하지 않았음을 명시한다. 문제가 없으면 없다고 명시한다.
